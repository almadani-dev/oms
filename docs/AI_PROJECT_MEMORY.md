# AI Project Memory

## Current Context

- OMS is a Laravel 13 + Filament 5 admin application (RTL, Arabic UI) for an organization's projects, donors and double-entry ledger (`transactions` / `transaction_lines`, per-currency, never blended).
- Financial writes go through six guarded workflows (receipts, project disbursement, execution payments, general expenses, general exchanges, opening balance), each in one `DB::transaction()` with server-side guards, description builders, both report projections and one audit event.
- Reports: Account Statement, Comprehensive Financial Transactions and (since 2026-10-13, committed `4b9f8c8`) the Donor Financial Report read real-time projections; their exports are «تصدير البيانات CSV» (detail rows) and «تصدير الإحصائيات Excel / Word» (statistics only). Background work runs on the `reports` queue; `oms:purge-report-snapshots` runs hourly.
- Local development runs both sites in separate FastCGI pools; synthetic load testing uses the guarded `oms_stress` database. Details: `## Operational Reference` below.
- Current state as of 2026-10-11: the Account Statement redesign and report exports are committed locally (not pushed); hashes are in the TASKS_LOG `### Commit Hash` sections.

  - **Found in production:** an active historical transaction dated year 0025 (`GEN-0025-0001`) made the rebuild skip the latest month's aggregates (verifier: 0 line differences, 2 monthly-total + 1 transaction-count differences, all April 2026). **Ledger semantics**
- `transaction_lines.debit_base` / `credit_base` are NOT base-currency figures: they always equal `amount_currency` on the debit or credit side, in the line's own currency (never × `fx_rate`). Any cross-account sum must be scoped to one currency (why Trial Balance requires `currency_id`). Reports never mix currencies.
- `accounts.current_balance` is a real persisted column (reconciled by `oms:check-financial-integrity`) but must never be used for report totals; reports compute from `transaction_lines`.
- There is no account nature (asset / liability / equity): `accounts_type` rows are cash / bank / wallet / partner categories only, and every account is debit-normal (a debit increments `current_balance`, a credit decrements it). Opening balances always debit the target account, so the «أرصدة افتتاحية» clearing accounts carry negative balances by design.
- `SUM(debit_base) = SUM(credit_base)` per transaction is valid only for the 3 single-currency flows (receipts, execution payments, general expenses). Disbursements and general exchanges balance by the FX equation in `FinancialTransactionBalanceGuard::assertBalancedMultiCurrencyLines()`: `credit(source) − debit(admin) − debit(transfer) = afterDeductions` and `destination.debit_base = afterDeductions × fx_rate` — two same-currency equations, never one cross-currency sum.
- `transactions.description` is system-generated on every create / edit of the 6 financial write flows — never user-editable there. `TransactionResource` (`admin/transactions`) and `TransactionLineResource` are read-only / audit-only end to end.
- `transaction_lines.description` / `line_role` are system-generated display / search / audit metadata, never a source of truth for amounts. `line_role` values come only from `App\Enums\TransactionLineRole`. Calculations (e.g. the Donor report's admin / transfer deductions) match on `transaction_lines.notes` and the per-model `LINE_*` constants; moving any calculation from `notes` to `line_role` needs a separately approved report-impact audit.
- `php artisan transactions:backfill-descriptions --dry-run` shows classified / unclassified historical rows; it is idempotent and safe after imports or restores, and leaves unclassifiable transactions untouched (reported by id).
- Execution payment: the credit account is user-editable, but `project_cost_budgets_payments` has no account column — the used credit account is only recoverable from the active line with `notes = ProjectCostBudgetsPayment::LINE_CREDIT` (`line_role = execution_source`), as `EditExecutionPayment::mutateFormDataBeforeFill()` does. `ExecutionPaymentForm::budgetDestinationLine()` is the budget's destination line (auto-default / currency only) — never use it to read back a payment's credit account.
- `oms:clean-operational-data --dry-run` audits orphan attachment files and only reports them (6 found on 2026-07-15, left by the 2026-07-06 TRUNCATE reset).

**Backups (Task 7B)**
- Content: a full `mysqldump` of the MySQL connection plus `storage/app/private/attachments` (`storage/app/public` excluded). Table `backup_operations` (SoftDeletes, UUID, `type` manual / daily / weekly / pre_restore / restore, `scope` database / files / full, status machine, nullable-unique `deduplication_key`). Private `backups` disk (`storage/app/private/backups`, `serve => false`, never symlinked; `.work/{uuid}/` scratch always removed).
- Archive: ZIP (`manifest.json`, `database/dump.sql`, `files/attachments/**`) in `SecretstreamEnvelope` (libsodium `crypto_secretstream_xchacha20poly1305`, chunked, versioned; never Laravel `Crypt`). `BackupKeyRing` reads `OMS_BACKUP_ENCRYPTION_KEY` / `OMS_BACKUP_ENCRYPTION_KEY_ID` / `OMS_BACKUP_PREVIOUS_KEYS` and fails closed.
- `BackupCreationOrchestrator` encrypts to `.enc.partial`, decrypts and fully verifies it (`BackupArchiveContentVerifier`: manifest, UUID / type / scope, dump and attachment SHA-256, exact entry set) before atomically publishing `{type}_{Ymd_His}_{uuid8}.omsbak.enc` and setting `completed` + `verified_at`. A failure leaves no completed row, file or plaintext; errors pass through `BackupErrorSanitizer` (no absolute paths, no `MYSQL_PWD`).
- `DatabaseDumper` streams `mysqldump` stdout to `dump.sql.partial` (`SymfonyProcessRunner`: `start()` + `getIterator()`, never `disableOutput()`); `MYSQL_PWD` only in the child environment; stderr bounded to 4 KB and sanitized. Symlinks are always rejected (`SymlinkDetector`); a real Linux symlink-escape rehearsal is still owed (Task 7D staging).
- Concurrency: scheduled backups use a deterministic `deduplication_key` (`daily:{Y-m-d Asia/Gaza}:{scope}`, `weekly:{ISO-year}-W{ISO-week}:{scope}`) enforced by the UNIQUE constraint; global `Cache::lock('oms-backup-operation')`; per-backup `BackupFileLock` (`oms-backup-file:{uuid}`) held for the whole download stream (HTTP 423 when held), integrity verification and deletion; retention skips locked rows.
- Jobs `CreateBackupJob`, `VerifyBackupIntegrityJob`, `RetentionCleanupJob` run on the `backups` queue. Schedule (`bootstrap/app.php`, `->timezone('Asia/Gaza')`, `withoutOverlapping()->onOneServer()`): daily 02:00, weekly Friday 02:30, retention 03:00 (the app timezone is Asia/Jerusalem).
- Authorization: `BackupAuthorization::check()` = the real Super Admin role AND the specific `backups.*` permission, re-checked inside every action closure and in `BackupDownloadController` (`GET /backups/{uuid}/download`). `backups.*` (including `backups.restore`) is Super-Admin-only by construction.
- `BackupManagementPage` («النسخ الاحتياطي والاستعادة», slug `backup-management`): stats widget, manual backup and verification are queued (never synchronous), download only via the `backups.download` route, single-record deletion with typed `DELETE`, 10 s polling, database notifications (`BackupOperationNotification`: manual → the initiator; scheduled → every active Super Admin). Messages never contain keys, passwords, absolute paths, `stored_path`, commands or stack traces.
- Deletion (`BackupDeletionService`, one rule order shared by `eligibility()` and `delete()`): refused when already deleted, active, `restore_activity_in_progress`, `is_protected`, the last known-good completed + verified backup, a referenced `pre_restore` backup, the source of a non-terminal restore (`restore_source_in_use`), or locked. The «إمكانية الحذف» column shows the same decision. Manual backups default to `is_protected = false`; retention always keeps manual backups.
- `BackupLabels` and the page's status-color `match()` have no default arm: every new `BackupType` / `BackupStatus` case needs a label.

**Restore engine (Task 7C) — developer invariants** (operator steps: Operational Reference → Restore recovery runbook)
- Restore rows reuse `backup_operations` (`type = restore`, `restore_metadata` JSON — bounded, phase history ≤ `BackupOperation::RESTORE_METADATA_MAX_PHASE_HISTORY_ENTRIES` = 50, never phrases / passwords / keys / commands — and `launch_nonce`). `BackupStatus::RestorePartial` is terminal; `isSuccessfulOutcome()` is true only for `Completed` / `Restored`. Private `restores` disk (`storage/app/private/restores`); config `oms.backup.restore` (`progress_schema_version`, `heartbeat_seconds`, `stale_after_minutes`, `min_free_space_reserve_bytes`, `free_space_margin_percent`, `attachments_denied_extensions`, `mysql_import_timeout`, `php_binary`, lock / rename retry settings).
- Locking: `BackupSubsystemLock` is an OS `flock()` on `{restores disk}/.locks/subsystem.lock` — never a DB-backed `Cache::lock` (cache and sessions use the `database` driver, which a restore replaces). The restore holds it exclusively for its whole process; every ordinary backup operation takes it shared first, then its Cache / per-backup lock, and then checks `RestoreActivityGuard::blocksOrdinaryOperations()` (a `Restoring` row, or a valid or tampered non-terminal progress file; a merely `Queued` restore never blocks). The safety backup uses `BackupCreationOrchestrator::runWithLockAlreadyHeld()` with a validated live exclusive handle.
- Signed progress: `RestoreProgressSnapshot::create()` validates every field (fixed scopes / phases / results). `RestoreProgressSigner` = HMAC-SHA256 keyed from `APP_KEY` (not the backup key ring). `RestoreProgressWriter`: temp file → `fflush` → `fsync` (failure aborts without touching `progress.json`) → copy to `progress.previous.json` → `rename` (Windows-only bounded retry `progress_publish_retry_*`) → best-effort directory `fsync`. `RestoreProgressReader` verifies the signature first, caps reads at 256 KiB and checks the UUID matches its directory.
- `RestoreActivityGuard::isActive()` → `Active` / `TamperedOrInvalid` / `Inactive`: active if a non-terminal restore row OR a valid signed non-terminal progress file exists (only UUID-named directories are scanned); tampered blocks a new restore like an active one. `$excludeRestoreUuid` ignores only a VALID non-terminal file of that UUID.
- Preflight (`RestorePreflightChecker`, non-destructive, before maintenance mode): source exists, not trashed, not a restore row, `Completed`, `verified_at`, archive exists (`SafeBackupPath`); scope compatibility (`database` ← database / full, `files` ← files / full, `full` ← full only, `RestoreScopeCompatibility`); key resolvable via `SecretstreamEnvelope::peekKeyId()` + `BackupKeyRing::resolve()` without decrypting; database scope: `oms.backup.mysql_client_path` exists (`is_executable()` on non-Windows only) and a complete mysql connection; files scope: restores disk and the `attachments` parent on one filesystem (`FilesystemIdentity`); no other active / tampered restore; then the disk-space estimate.
- Disk space (`RestoreDiskSpaceEstimator`, checked before any workspace exists): source decrypted archive + staging (`original_size_bytes` each, else 4 × encrypted size) + current database (`CurrentDatabaseSizeEstimator`, `information_schema`, fallback max(source, 50 MiB)) + current attachments (always) + 3 × (current DB + attachments) for the FULL safety-backup pipeline + quarantine (files scope) + 100 MiB; × (1 + `free_space_margin_percent`) and floored at `min_free_space_reserve_bytes`.
- Workspace / extraction: `RestoreWorkspace` = `restores/{uuid}/workspace/` (every path via `SafeBackupPath`, root containment and a symlink walk; `cleanup()` deletes only that subtree; no age-based sweep). `RestoreArchivePreparer`: preflight → workspace → `SecretstreamEnvelope::decryptFile()` → `BackupArchiveContentVerifier::verify()` → `RestoreArchiveExtractor::extract()`; failures clean up best-effort without masking the original error and never modify the source archive. The extractor never uses `extractTo()`: entries come only from the verified manifest, the full manifest entry set is re-matched against the ZIP, paths are safety / duplicate-checked, non-regular entries rejected, and each entry is streamed in 1 MiB chunks within per-entry and total byte budgets and SHA-256 checked.
- Launch: `RestoreRequestService::createQueuedRestore()` is the only creator of queued restore rows (eligibility and scope re-checked on a fresh read inside the exclusive lock; one queued / restoring restore at a time; nonce `bin2hex(random_bytes(32))`). `RestoreLaunchService::launch(uuid, nonce)` validates the row (no forbidden secret keys in `restore_metadata`) → exclusive lock (else 423) → activity guard excluding itself (409) → atomic conditional `UPDATE … WHERE status = 'queued' AND started_at IS NULL AND launch_nonce = ?` (query-builder updates need `restore_metadata` json-encoded by hand) → signed progress `launching` → `RestoreProcessLauncher::launch()`; failures mark `RestoreFailed`; the lock is released in `finally`. Signed route `POST /restores/{uuid}/launch` (`restores.launch`; no GET) → `RestoreLaunchController` re-checks the Super Admin role AND `backups.restore`.
- Launchers: `LinuxDetachedRestoreProcessLauncher` argv `[setsid, --fork, php_binary, artisan, 'oms:restore', uuid]` (no shell, `disableOutput()`, `cwd = base_path()`, fail-closed binary checks). `WindowsDetachedRestoreProcessLauncher` is local-only and may not survive the request (runbook). Production php-fpm must set `OMS_RESTORE_PHP_BINARY` (`PHP_BINARY` is not CLI there).
- `php artisan oms:restore {uuid}`: never queued, never uses the Cache lock; requires a claimed row (`Restoring`, `started_at`, nonce consumed) and a valid non-terminal progress file; takes the exclusive lock with bounded retry (`launch_lock_retry_timeout_seconds` / `launch_lock_retry_interval_ms`), re-verifies, writes `lock_acquired` (`advanceToLockAcquired()`), then runs `RestoreOrchestrator`; exit 0 only for `Restored`.
- `RestoreOrchestrator` order: preflight → maintenance mode (entered only when not already down; ownership decided before `enter()`) → mandatory FULL safety backup (must be Completed + verified + archive present) → reconciliation snapshot written into signed progress at `safety_backup_completed` → decrypt / verify / stage → [files] attachment activation → [database] import → [database] reconciliation → [files] quarantine finalization → workspace cleanup → maintenance exit (only if this restore entered it) → terminal result. Terminal writes go through `RestoreTerminalResultWriter` (re-fetch by UUID, tolerate a missing row; the progress file is authoritative); the pre-import Eloquent row is never reused after the import.
- Compensation: failures before the destructive boundary → `RestoreFailed`; ambiguous attachment states → `RestorePartial`; DB-import failure after activation → automatic attachment rollback (success → `RestoreFailed` noting a possibly partial database; failure → `RestorePartial`); reconciliation or finalization failure → `RestorePartial` (never an automatic DB rollback; quarantine kept); progress-write failure after the import → `RestorePartial`; maintenance-exit failure → `RestorePartial` unless nothing destructive happened.
- `RestoreMaintenanceMode` is the only caller of `artisan down` / `up`, and calls `down` with no options (this Laravel's `down` has no `--message`). If the app was already down, the restore never brings it up.
- Heartbeats: `RestoreHeartbeat` (Carbon-based, throttled) ticks through the dump, decrypt and extraction chunks, staged revalidation, reconciliation steps, and a 200 ms poll loop in `SymfonyProcessStreamInputRunner` (which enforces the timeout itself via `checkTimeout()`); heartbeat write failures are compensated like phase writes.
- Database import (`DatabaseRestorer`): re-validates scope, staged dump (regular file inside the workspace, no symlink), mysql client and connection; restores only `config('database.default')` (`database_connection_mismatch` otherwise). argv `[mysql, --host, --port, --user, --default-character-set=utf8mb4, database]`, password only as `MYSQL_PWD`, dump streamed to stdin (`setInput(resource)`); failures → sanitized `RestoreDatabaseException`.
- Reconciliation (`RestoreReconciler`, fixed order, stops at the first failure, no outer transaction): connection reset (`DB::purge` + `select 1`) → `migrate --force` → `oms:sync-permissions` → `permission:cache-reset` → metadata reconstruction → ephemeral cleanup → `queue:restart`.
  - `RestoreMetadataUpserter` upserts the source, safety and restore rows by UUID `withTrashed()` from the signed `reconciliation_snapshot` (never the pre-import DB): clears `deleted_at`, forces the safety row `Completed` + `verified_at`, persists `manifest_version` (not `deduplication_key`), nulls `created_by` when that user no longer exists (identity kept in `restore_metadata['creator_identity']`). Numeric `backup_operations` IDs change after a database / full restore — relationships are resolved by UUID.
  - `RestoreEphemeralTablePolicy` deletes ALL `jobs` rows on the configured backups queue (other queues, `failed_jobs`, `job_batches`, `notifications` kept) and truncates `cache`, `cache_locks`, `sessions` (everyone re-logs in), each only if the table exists.
- Attachment restore: paths only via `RestoreAttachmentPaths`, as siblings of the live root `storage/app/private/attachments` — quarantine `attachments.pre_restore.{uuid}`, rollback scratch `attachments.restore_discard.{uuid}`, signed marker `attachments.pre_restore.{uuid}.state.json` (outside the disk root, so `AttachmentCollector` never sees them).
  - `RestoreAttachmentRevalidator::revalidate(RestoreAttachmentManifest)` runs right before the first live rename: exact file set, unique normalized paths, no symlinks / reparse points / special files, per-file size + SHA-256, total budget, and the denylist `attachments_denied_extensions` (`php`, `phtml`, `phar`, `exe`, `sh`, `bat`, `cmd`, `dll`, `htaccess`) case-insensitively on every dot segment of the basename.
  - `RestoreAttachmentActivationService` (behind `RestoreAttachmentLifecycle`; the exclusive handle is re-validated on every call): `activate()` only from `NotActivated` (live → quarantine, staged → live; emergency quarantine → live on failure), `rollback()` from `Activated` / `InterruptedDuringActivation` / `InterruptedDuringRollback` (never deletes the last copy), `finalize()` only from `Activated` (symlink-safe bounded delete of the quarantine, verified gone).
  - The marker is signed (`AttachmentSwapMarkerWriter` / `Reader`, HMAC from `APP_KEY` with context `oms-restore-attachment-swap-v1`, same durability seam as progress files) and write-ahead: phases are persisted before and after every rename; a marker failure after a mutation stops with `marker_update_failed_after_mutation`. `AttachmentSwapStateInspector` maps any marker integrity failure to `InconsistentNeedsManualReview`.
  - Renames: Linux = one atomic `rename()`; Windows = bounded retry (`NativeAttachmentMoveRunner`, `attachment_move_retry_attempts` / `attachment_move_retry_delay_ms` = 5 / 200 ms).
  - A files-only restore leaves the database untouched: attachment rows created after the backup may point to missing files (fails safely), and its row gets no `pre_restore_safety_backup_id` (the link stays in the signed `reconciliation_snapshot`).
- Watchdog / UI: `oms:restore-watchdog` (every minute) is detection only; DB and disk scans are guarded independently (`database_unavailable_during_detection`), the per-(UUID, reason) notification cooldown is best-effort in Cache. Notifications `RestoreSucceeded` / `RestoreFailed` / `RestorePartial` / `RestoreStale` go through `BackupNotifier`.
  - The «استعادة» row action appears only when `canOfferRestore()` passes (Super Admin + `backups.restore`; completed, verified, not trashed, not a restore row; archive present; a compatible scope; no active restore). Two-step wizard: scope, reason, typed `RESTORE {uuid8}` (`dehydrated(false)`, never stored), then a final confirmation. Outcomes become sanitized Arabic notifications, never auto-retried.
  - `RestoreStaleAcknowledgmentService` is the only way to terminalize a stale restore: only for the exact `stale_heartbeat` reason and when the exclusive lock can be briefly acquired; typed `ACKNOWLEDGE {uuid8}`; it writes the signed terminal progress first (failure propagates), then best-effort updates the row with `restore_metadata.stale_acknowledgment`. A tampered state hides both actions and shows a manual-review message. `crashed_acknowledged` is a `restore_failed_phase`-only value; `RestorePhaseLabels` maps the real phases to Arabic.
  - `GET /restores/{uuid}/progress` (`RestoreProgressPollController`) is authorized by `signed` only, strips the session / cookie / CSRF middleware, is excluded from maintenance mode (`preventRequestsDuringMaintenance(except: ['restores/*/progress'])`), runs zero DB queries and returns a fixed sanitized field set.

### Restore recovery runbook (formerly `docs/RESTORE_RECOVERY.md`; OMS Tasks 7C.7–7C.9)

For a restore that is stuck, crashed or ended `RestorePartial`. Read `RestoreOrchestrator`'s docblock first. Never put an encryption key, database password or confirmation phrase in any note, ticket or log excerpt.

- **Identify an active / stale restore (check both):** a `backup_operations` row with `type = restore`, `status = restoring`; and a non-terminal (`result = null`) signed `storage/app/private/restores/{uuid}/progress.json` (disk from `config('oms.backup.restore.disk')`). The scheduled `oms:restore-watchdog` (every minute) compares `last_heartbeat_at` with `oms.backup.restore.stale_after_minutes` (20) and notifies. Detection only: it never mutates, retries, resumes or locks.
- **Normal first step (7C.8):** «النسخ الاحتياطي والاستعادة» (`BackupManagementPage`) shows a Super-Admin-only «تأكيد أن عملية الاستعادة السابقة متوقفة» action when `RestoreStaleAcknowledgmentService` finds a restore eligible: validly signed, non-terminal, heartbeat older than `stale_after_minutes`, and no live process holding the restore subsystem's lock.
  - It only writes a terminal signed snapshot (`result = restore_failed`, `restore_failed_phase = crashed_acknowledged`) and marks the row `RestoreFailed` with a `restore_metadata.stale_acknowledgment` audit record (who, when, reason).
  - It never rolls back, changes maintenance mode, deletes workspace / quarantine or relaunches; afterwards treat the restore as failed at the last `phase_history` entry before the acknowledgment. It only unblocks a NEW restore.
  - A tampered / unreadable progress file is never offered this action (the UI shows «تم اكتشاف حالة استعادة غير موثوقة») and needs the manual steps below.
- **Live progress without the admin panel:** `GET /restores/{uuid}/progress` (short-lived signed URL, `RestoreProgressPollController`) works in maintenance mode and without the database; it reads only `progress.json`.
- **Progress files:** `progress.json` (authoritative) and `progress.previous.json` (recovery copy). Never edit them: they are signed (`RestoreProgressSigner`), and a tampered file is `TamperedOrInvalid`, which blocks new restores for manual review. Read them with `cat` / `Get-Content` or `RestoreProgressReader` in tinker. Key fields: `phase`, `phase_history`, `result`, `restore_failed_phase`, `error_summary`, `last_heartbeat_at`, `reconciliation_snapshot`.
- **Safety backup:** every restore first takes a mandatory FULL `BackupType::PreRestore` backup, whatever its own scope. Its UUID is in `pre_restore_safety_backup_uuid` and in `reconciliation_snapshot.safety_backup.uuid` (from `safety_backup_completed` on; survives a lost database). It is usable only if its `backup_operations` row is `completed` with `verified_at` set and its encrypted archive exists on the backups disk.
- **By phase:**
  - **At or before `staging`** (never reached `database_restoring`): the live database is untouched. Without `attachments_swapped` in `phase_history`, nothing destructive happened: re-launch later with a fresh UUID. With it, see the attachment states below.
  - **`database_restoring` failed or interrupted:** the database may be partial. Do not run `php artisan up`. Keep maintenance mode until a Super Admin decides between the safety backup (pre-restore state) and re-running the source backup.
  - **`database_restored` reached, `restore_partial` at or after `reconciling`:** the import succeeded, but one of migrations, permission sync, permission cache reset, metadata reconstruction, ephemeral cleanup or `queue:restart` failed (`error_summary`; `RestoreReconciliationException` `reasonCode`, e.g. `migration_failed`, `permission_sync_failed`, `metadata_reconstruction_failed`, `ephemeral_cleanup_failed`, `queue_restart_failed`). The database is never rolled back automatically, and the attachment quarantine is left intact — do not delete it. Fix the root cause and re-run the remaining step by hand under Super Admin supervision (reconciliation alone cannot be resumed).
  - **`restore_partial` at `finalizing`:** the restored live attachments are correct; only the disposable quarantine could not be deleted. Safe to leave; delete it only after confirming the live attachments. A failed cleanup of the plaintext `restores/{uuid}/workspace` alone never downgrades a `Restored` outcome; delete it by hand once the terminal result is confirmed.
- **Attachment states** — inspect, never guess: `(new \App\Services\Restore\Attachments\AttachmentSwapStateInspector())->inspect($restoreUuid)`.
  - `NotActivated`: live attachments untouched.
  - `Activated`: live = the restored tree; the original is intact in `attachments.pre_restore.{uuid}`.
  - `InterruptedDuringActivation`: live attachments missing, the original safe in quarantine; resume with `RestoreAttachmentActivationService::rollback()`.
  - `InterruptedDuringRollback`: the restored tree was moved to `attachments.restore_discard.{uuid}`, the original is not back yet; also resumable by `rollback()`.
  - `InconsistentNeedsManualReview`: the signed marker (`attachments.pre_restore.{uuid}.state.json`) and the directories disagree; a developer / Super Admin inspects both before any action.
- **Maintenance mode:** `phase_history` with both `maintenance_enabled` and `maintenance_disabled` means the restore entered and left it. With only `maintenance_enabled` (and no clean `Restored`), the restore may still own it or failed at `maintenance_disabled`: confirm the data is consistent before `php artisan up`. If the application was already down before the restore started, the restore never brings it up; that is a separate operator decision.
- **Safe to run:** read-only tinker (`BackupOperation`, `RestoreProgressReader`); `php artisan oms:restore-watchdog` (idempotent); `php artisan up` only after the data / attachment state is confirmed safe; restoring the safety or source backup through the normal confirmed launch flow once a Super Admin has decided.
- **Never:** hand-edit the progress files; rename or move `attachments`, `attachments.pre_restore.{uuid}` or `attachments.restore_discard.{uuid}`; delete a quarantine / discard tree before the live tree is confirmed; run `up` just because a restore "looks stuck"; re-run `oms:restore {uuid}` for a terminal or ambiguous UUID; delete or truncate `backup_operations` rows; resume, retry or "finish" a restore by script.
- **Linux production:** `rename()` of the progress file and of the attachment swap is atomic on one filesystem, so a crash leaves one of the defined states above. Maintenance mode is Laravel's `down` / `up` flag file under `storage/framework/`. The restore process is detached with `setsid` (`LinuxDetachedRestoreProcessLauncher`) and keeps running after the launching request ends.
- **Windows / Laragon (local only):** `rename()` is not POSIX-atomic and directory `fsync` is unsupported (`RestoreProgressWriter`). `is_executable()` is unreliable, so an existing `mysql` / `mysqldump` file counts as runnable. Confirmed in 7C.9: `WindowsDetachedRestoreProcessLauncher` can leave a clicked restore frozen at `phase = launching` (row `Restoring`, no `php.exe`, no error). That is not a data-safety issue: run `php artisan oms:restore {uuid}` in the foreground with the same UUID (`RestoreCommand::isClaimedForExecution()` accepts it), and do not click «استعادة» again meanwhile (`RestoreActivityGuard` rejects it).

### Account Statement architecture (formerly `docs/ACCOUNT_STATEMENT_ARCHITECTURE.md`; 2026-10-07 → 2026-10-11)

Multi-account, multi-select, real-time تقرير كشف الحساب over a synchronously maintained projection; the ledger stays the only source of truth. The approved business rules are in the 2026-10-07 redesign bullet under Recent Changes and in DECISIONS_LOG 2026-10-07. In addition: filter algebra is empty = no condition, values of one filter = IN (OR), different filters = AND, classifications ∩ types = intersection; soft-deleted types still label their rows; the default period is the first of the current month → today; with a dimension filter, opening + debit − credit ≠ closing, and the page and exports say so.

- **Tables** (migration `2026_10_07_100000`, no FKs):
  - `account_statement_lines`: one row per active line of an active transaction (IDs, time, type, project cost, line currency, statement debit / credit). PK `(account_id, transaction_time, line_id)`; indexes `line_id` (unique), `transaction_id`, global order `(transaction_time, line_id, transaction_type_id)`, project `(project_cost_id, transaction_time, line_id)`.
  - Checkpoints: `account_statement_daily_totals` (account × day × currency), `account_statement_monthly_totals` (account × month × type × currency), `account_statement_account_totals` (account × currency, all-time).
  - `account_statement_projection_state`: `ready` / `building` / `invalid` / `missing`; only `ready` is read. An empty ledger starts `ready`; an existing ledger starts `missing` until rebuilt.
  - Labels, descriptions and notes are never copied; they are joined from the ledger for the ≤ 50 visible rows, so a rename rewrites nothing.
- **Maintenance:** `AccountStatementProjector`, reached only through `ComprehensiveReportProjector::syncTransactions()` / `removeTransaction()` inside each write path's own `DB::transaction()` (receipt, general expense, general exchange, project disbursement and execution payment create / edit / delete; opening balance on account creation). It re-derives the transaction's rows from the ledger and moves the checkpoints by the exact difference (bcmath), locking in a fixed order (lines, daily, monthly, all-time; keys sorted). Any failure rolls everything back. Backdating touches only the affected account × day / month / all-time rows. The existing static test fails if a ledger write site does not reach the projector.
- **Reading** (`app/Services/Reports/AccountStatement/`):
  - `AccountStatementFilters`: normalized applied filters (integer, positive, unique, sorted ID lists).
  - `AccountStatementScope`: accounts as a literal ID list of non-deleted accounts (a sub-select only above 20,000); classifications ∩ types → type IDs (deleted types included); projects → cost IDs (deleted cost items included).
  - `AccountStatementBalances`: balance before (time, line) = Σ monthly before the month + Σ daily in the month before the day + that account's earlier lines of the day; a day-boundary prefix is read directly or as all-time − suffix, whichever side has fewer months; type-filtered totals = typed monthly totals + partial edge months; project totals through the project index; mixed-currency candidates from the all-time totals, then checked exactly for the period.
  - `AccountStatementRows`: keyset pages in canonical order, plan chosen once per «عرض» from exact counts — MERGE (per-account PK ranges, `UNION ALL`, `LIMIT 50`), SCAN (global order index), PROJECT (project index).
  - `AccountStatementReport`: `summarize()` («عرض» only, O(accounts)), `accountSummaries()` (25 per page), `page()` (≤ 50 rows), `rows()` (chunks of 1,000). Running balance of a row = balance before it + its debit − its credit.
- **Pager and state:** pages aligned on multiples of 50; Last fetches only the remainder (reverse keyset), so Previous from Last lands where Next would; no OFFSET. Livewire state holds only the applied filters, small labels, the per-currency summary, cursors `[time, line]`, page numbers and the 25-account summary page — never rows.
- **Exports (final, 2026-10-11):** «تصدير البيانات CSV» (movements only; inline ≤ 25,000 units, otherwise the `reports` job) · «تصدير الإحصائيات Excel» (one worksheet «الإحصائيات»; always inline; no limit) · «تصدير الإحصائيات Word» (the same `Statistics\StatisticsReport` model via `AccountStatementStatistics`; refused only above `word_max_summary_rows` = 2,000 accounts + currencies). Thresholds: `config/oms.php` → `reports.account_statement`. The legacy detail-Excel code is kept but unreachable; the detail Word service was deleted.
- **CSV** (`app/Services/Reports/AccountStatement/Csv/`):
  - **Package:** `كشف_الحساب_YYYYMMDD_HHMMSS.csv` when planned as one file of ≤ `csv.plain_max_rows` (100,000) movements; otherwise a `.zip` of `حركات_كشف_الحساب.csv`, or `حركات_001.csv`… above `csv.max_rows_per_file` (1,000,000), cut on day boundaries. Never truncated; no summary file.
  - **14 columns:** التاريخ / الوقت, رقم الحركة, نوع المعاملة, تصنيف المعاملة, الوصف, البيان / ملاحظات السطر, دور سطر القيد, وصف سطر القيد, المشروع, الحساب, العملة, مدين, دائن, الرصيد الجاري.
  - **Encoding** (`AccountStatementCsvFormat`): UTF-8 with BOM, comma, CRLF, RFC 4180 quoting. Money as plain numbers from integer cents or the DECIMAL string, never through a float. Text starting with `= + - @`, a tab or a carriage return gets a `'` prefix; numeric cells are never touched. Null text is empty; line role / description use the screen's `—`.
  - **Reading** (`AccountStatementCsvSegment`): day-aligned segments planned from the monthly counts; each segment is one unbuffered query over the projection (SCAN path, or PRIMARY for a few accounts holding a small share), LEFT JOINing the row's own `transaction_lines` / `transactions` texts; every other label from maps loaded once (`AccountStatementCsvLabels`). Running balance: an integer-cents map per account from `AccountStatementBalances::prefixByAccount()`; lines hidden by dimension filters move it, but their texts are not read.
  - **Parallelism:** the queued job runs up to `csv.workers` (8) hidden CLI processes `oms:account-statement-csv-segment` (refuses specs outside the work directory and any other database), each with its own connection and snapshot. Pieces are DEFLATE level 1 (`AccountStatementCsvPart`) and joined by `AccountStatementCsvZip` (each byte copied once, CRC-32s combined, UTF-8 names, ZIP64 only when needed); a plain `.csv` is stored pieces concatenated once (`AccountStatementCsvPart::concatenate()`).
  - **Proof before delivery,** per account: segment k's closing = segment k+1's opening; the first opening, last closing, listed lines, debit and credit = the account summary. A difference (a write between the parallel snapshots) rebuilds (`csv.attempts` = 2); an inconsistent file is never delivered.
  - **Delivery:** inline up to `csv.inline_max_units` (25,000 = movements + 5 × accounts); above it `BuildAccountStatementCsvExportJob` on `reports`, polled through the JSON status endpoint `reports.account-statement.export-status`. Download route `reports.account-statement.csv` (Filament auth, signature, both permissions, owner only). Re-fetchable until it expires, audited once (`format csv`, `purpose detail_data`, filters, `exported_movements`, `exported_accounts`, `movement_files`, `package_type`, `package_bytes`, `generation_seconds`, `delivery`). One CSV export per user at a time (cache lock). `oms:purge-report-snapshots` removes expired packages and abandoned work directories.
- **Operations:** `oms:rebuild-account-statement-projection [--resume] [--untrusted] [--window=500] [--verify]` (ledger only, restart-safe; pass 1 lines per transaction-ID window, pass 2 checkpoints per account window in SQL) and `oms:verify-account-statement-projection [--window=2000] [--balance-samples=200]` (recomputes lines and every checkpoint from the ledger and samples balances; any difference marks the projection `invalid`, and the page refuses to show a statement). Rollback: the tables are additive; reverting the code leaves them unused; `migrate:rollback` of that migration drops them; drift is fixed by a rebuild.

5. **Benchmark:** «عرض» of the largest donor, pager moves, CSV / Excel / Word.
6. **Monitor:** the state row (`status`, `verified_at`, `note`); operator decision on a daily `oms:verify-donor-financial-report-projection` (drift → INVALID → automatic legacy fallback; repair with `--donor=ID` or a full rebuild).
7. **Rollback:** mark the state `invalid` (instant legacy fallback), or redeploy the previous release (tables unused) and `migrate:rollback` that migration. No business data is touched by either.
- Also: scheduler (`oms:purge-report-snapshots` still purges legacy donor state / CSV dirs), PHP-FPM one request per process (R1), InnoDB buffer pool (CSV text hydration is I/O-bound), storage permissions unchanged (no new directory). After any database restore: verify, rebuild on differences.

### Local runtime: both sites in separate FastCGI pools (formerly `docs/LOCAL_STRESS_RUNTIME.md`; dev machine only, not production)

- **Why:** Apache 2.4.62 (Apache Lounge, WinNT MPM, threaded) ran every site in one PHP 8.3.28 TS `mod_php` process. Without a config cache, process-wide `putenv()` / `getenv()` let concurrent requests see missing or foreign values: an empty `APP_KEY` (Livewire 4's endpoint hash changes from `/livewire-0e06790f` to `/livewire-4aeeedbb`, so valid POSTs got 404), `MissingAppKeyException` 500s, and sqlite / `production` / wrong-database fallbacks.
- **Now:** each site has its own mod_fcgid (`mod_fcgid-2.3.10-win64-VS16.so`) pool of `php-cgi.exe` workers — one request per worker, environment fixed at start, up to 16 workers, recycled after 1,000 requests, `SetHandler fcgid-script` inside `oms\public`. Files in `C:\laragon\etc\apache2\sites-enabled\`:
  - `05-oms-test-fcgid.conf` — `http://oms.test/admin` (`ServerName oms.test`, `ServerAlias *.oms.test`). Nothing injected, so `.env` → `local`, `oms`, `storage\`. It loads before Laragon's regenerated `auto.oms.test.conf` (Apache uses the first matching vhost; `httpd -S` lists the auto file second). Its wrapper (`php-cgi.exe -d variables_order=GPCS`) differs from the stress one, so the pools never share processes.
  - `10-oms-stress-lan-fcgid.conf` — `Host: 172.16.0.100` only: `http://172.16.0.100/oms/public/admin` with `APP_ENV=stress`, `DB_DATABASE=oms_stress`, `LARAVEL_STORAGE_PATH=…\storage\stress` (worker environment + per-request params). Every stress page shows the red banner «STRESS TEST ENVIRONMENT, SYNTHETIC DATA ONLY – بيئة اختبار الضغط (oms_stress)»; the normal site never does.
  - Any other host name for `/oms/public` (e.g. `http://localhost/oms/public`) still reaches normal `oms` through the default `mod_php` vhost — use the exact host names.
  - Disabled: `C:\laragon\etc\apache2\alias\oms-stress-dev.conf.off` (the old global `<Location "/oms/public"> SetEnv …`). Backups: `C:\laragon\etc\apache2\_backup_2026-10-07_stress-isolation\` and `C:\laragon\etc\apache2\_backup_2026-10-07_oms-test-isolation\`.
- **After a reboot:** start Laragon; Apache spawns both pools on each site's first request; no PHP command is needed for browsing. Restart Apache with **Stop**, then **Start** — a plain "Reload" was observed NOT to restart the Apache child. A queue worker is only needed for background exports (CSV above 25,000 work units) and the comprehensive snapshot fallback: `php artisan --env=stress queue:work database --queue=reports --timeout=1900` (without `--env=stress` for normal).
- **Return the LAN path to normal `oms`:** rename `10-oms-stress-lan-fcgid.conf` to `…conf.off`, then Stop + Start Apache.
- **Rollback:** `oms.test` → delete `05-oms-test-fcgid.conf` (Laragon's `auto.oms.test.conf` serves it again); stress → delete `10-oms-stress-lan-fcgid.conf` and rename `alias\oms-stress-dev.conf.off` back to `oms-stress-dev.conf`; then Stop + Start Apache. No database depends on the runtime.
- **Known Windows effect:** the first concurrent compile of a changed Blade view can fail a `rename()` transiently (Laravel on Windows, with either runtime). Verification numbers: TASKS_LOG 2026-10-07.

### Stress environment `oms_stress` (formerly `docs/STRESS_ENVIRONMENT.md`; local development only, synthetic data)

- **Absolute rules:** stress data lives only in the separate local MySQL database `oms_stress` — never in `oms`, never on a shared or production server. Nothing generates it automatically (not `DatabaseSeeder`, a migration, a composer / deploy script or application boot) — only the hidden `oms:stress:*` commands run by hand. `.env.stress`, `storage/stress/`, dumps, generated attachments, exports and snapshots are never committed (`.gitignore` covers `.env.stress` and `storage/stress/`). The stress password is never written to a file, log, doc or Git; it is stored only as a hash inside `oms_stress`.
- **Hard guards** (`config/oms_stress.php`, fixed lists not read from `.env`; enforced by `App\Services\Stress\StressEnvironmentGuard`):
  1. No APP_ENV source may be `production`; the environment must be `local`, `stress` or `testing`; writing commands require `stress` (or `testing`).
  2. Config must not be cached.
  3. `--database` must be exactly `oms_stress`; `oms` and system schemas are forbidden; outside the stress profile the app's default database can never be the target, and under it, it must be.
  4. MySQL host `127.0.0.1` / `localhost` / `::1`, and the live `@@hostname` must equal this machine's hostname.
  5. `--confirm=oms_stress` always; reset also `--confirm-reset=oms_stress`.
  6. Every command except create-database requires the `_stress_meta` marker table (naming `oms_stress`) in the target.
  7. `SELECT DATABASE()` must equal `oms_stress` before anything is written.
  8. Writing commands require `storage_path()` to be exactly `storage/stress`.
- **One-time setup:** copy your local `.env` to `.env.stress` (same DB credentials and APP_KEY) and change only `APP_ENV=stress`, `DB_DATABASE=oms_stress`, `LARAVEL_STORAGE_PATH=C:\laragon\www\oms\storage\stress` (see `.env.stress.example`).
- **Commands** (always `--env=stress`; hidden from `php artisan list`):

  ```
  php artisan --env=stress oms:stress:audit --scale=large          # read-only pre-flight (also allowed without --env)
  php artisan --env=stress oms:stress:create-database --database=oms_stress --confirm=oms_stress
  php artisan --env=stress oms:stress:build  --database=oms_stress --confirm=oms_stress --scale=small --seed=20261005
  php artisan --env=stress oms:stress:verify --database=oms_stress --confirm=oms_stress
  php artisan --env=stress oms:stress:reset  --database=oms_stress --confirm=oms_stress --confirm-reset=oms_stress
  ```

  - `create-database`: creates the empty database, runs the real migrations, checks schema parity against the CURRENT code (a temporary `oms_stress_schema_ref_<12 hex>` migrated from zero; only the marker table may differ; the reference is always dropped, also by the next `create-database` or `reset`), copies the 8 lookup tables from `oms` through a READ ONLY session, runs the real `PermissionSyncService`, prepares `storage/stress/`, writes the marker. `oms` is never migrated by any stress command.
  - `build`: refuses a non-empty database. Scales `small` (~10k lines), `medium` (~100k), `large` (~535k) or `--lines=N`; same seed + code + schema → same dataset; fail-clean (on error: reset and rebuild). Line payloads come from the current Create pages' own builders and pass the real `FinancialAmountGuard` / `FinancialTransactionBalanceGuard`; `current_balance` is set from the generated ledger; audit history comes from the real snapshotters; project snapshots from `reports:refresh-projects-financial --force`. Runtime-only data (sessions, jobs, snapshots, exports, notifications, backup operations) is not generated.
  - `verify`: read-only; exits non-zero on any violation. Never run a larger build after a failed verify.
  - `reset`: drops `oms_stress` and deletes `storage/stress/` (never `migrate:fresh`, never `oms`).
  - **After every `build`,** rebuild the comprehensive report projection (`php artisan --env=stress oms:rebuild-comprehensive-report-projection --verify`): the generator bulk-inserts the ledger and bypasses the projectors. The Account Statement projection on `oms_stress` was rebuilt the same way on 2026-10-07 (`oms:rebuild-account-statement-projection --verify`).
- **Using it:** CLI commands and workers with `--env=stress`; the browser through the LAN site (local runtime above) or `$env:APP_ENV = 'stress'; php artisan serve --host=127.0.0.1 --port=8081; Remove-Item Env:APP_ENV` (loopback only; every page shows the red stress banner). Never `config:cache` while switching profiles. Users are `stress.<role>@stress-oms.invalid` (`super_admin`, `admin`, `accountant`, `accountant_2`, `pm`, `pm_2`, `viewer`; `accountant_former` inactive); the password from `oms:stress:build --generate-password` is shown once and stored only as a hash.
- **Current dataset** (2026-10-05, `--lines=1150000`, seed 20261005): 1,233,324 lines (1,221,321 active), 555,923 transactions, ~616k audit events, 5,043 accounts, 6,446 projects, 2,578 Muwakha families; `oms:stress:verify` 0 violations. Build and benchmark history: TASKS_LOG 2026-10-05.
- **Return to normal OMS:** stop the stress server (Ctrl+C) and any `--env=stress` worker; run commands without `--env=stress`. `oms`, `.env` and `storage/` are never used by the stress profile.

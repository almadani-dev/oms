## Important Notes

- `transaction_lines.debit_base`/`credit_base` are **not** converted-to-company-base-currency figures despite the name — they always equal `amount_currency` placed on the debit or credit side, in the line's own currency (confirmed by tracing `CreateGeneralExpense.php`/`CreateGeneralExchange.php` write paths, including cases where `fx_rate != 1`). Any report that sums these fields across accounts must scope to a single currency at a time, or totals will be silently blended and misleading. This drove the Trial Balance's required `currency_id` filter.
- `accounts.current_balance` must never be used for report totals (per project rule and confirmed audit finding) — Trial Balance computes everything from `transaction_lines` directly.
- The system has **no account nature** (asset/liability/equity): `accounts_type` rows are cash/bank/wallet/partner categories only. Every account is uniformly debit-normal — a debit line always `increment`s `current_balance`, a credit line always `decrement`s it, in every financial page. The opening-balance feature follows this convention (target account always debited); clearing accounts "أرصدة افتتاحية" therefore carry negative balances by design.
- `transactions.description` is now system-generated on every create/edit of the 6 financial write flows (see 2026-07-14 entries above) — never expose it as a user-editable field on those 6 flows' forms. The raw `TransactionResource` admin CRUD (`admin/transactions`) is now **read-only/audit-only** end to end (see the 2026-07-14 "read-only audit resource" entry above) — its `description` field is `disabled()->dehydrated(false)` and its create/edit routes, actions, and authorization are all disabled, so this class of overwrite risk is closed.
- `transaction_lines.description` and `transaction_lines.line_role` (added 2026-07-14) are system-generated, additive metadata only — display/search/audit, never a source of truth for accounting amounts, never parsed by any report/calculation. `line_role` values must come from `App\Enums\TransactionLineRole` only; `transaction_lines.notes` and the per-model `LINE_*` constants remain the authoritative tags that edit flows and reports (e.g. Donor Financial Report deductions) actually match on — do not migrate any reader from `notes` to `line_role` without a separately approved report-impact audit. Historical lines keep both fields NULL (no backfill); UI columns must stay null-tolerant.
- This repo's migrations cannot currently run cleanly via `migrate:fresh`/`RefreshDatabase` end-to-end — `2026_06_24_000005_backfill_denormalized_currency_and_amounts.php` uses MySQL-only `UPDATE ... JOIN` syntax. Any future test needing the full stack will hit this; either mock around it (as `TransactionDescriptionBuilderTest` does) or get explicit approval to rewrite that backfill migration's SQL to be cross-database compatible.
